# Code structure and development

[← Docs](README.md) · [中文](../development.md)

Zero dependencies, no transpiling: the source is split into many parts, and when `/support.js` (`prompts/` first, then `src/`) or `/app.css` is requested, the bridge concatenates them in path order on the fly (subfolders expanded in place), with the ETag taken from each part's size and modification time. Change a part and reload; nothing is written to disk, and there's no built output in the repository.

| Folder / file | Contents |
| --- | --- |
| `src/` | Page scripts, split by domain and concatenated into one closure: `00-state` is the data model (Store / Conversation / Message / Step / Profile… as JSDoc typedefs at the top) and cross-domain page state; `01-bridge` is the single channel for talking to the bridge (connecting, the bus, `bridge()`); `01-store/` is storage (each part carries its own constants and bookkeeping, and `90-open` reads `store` once they're set up). After that come chat data, brush icons and small utilities, Markdown, startup, the two modes and the welcome page (`06-mode-welcome/`: folder and permission level, the welcome page, folder and attachment tags, opening and closing chats), rendering and drawing (`07-render/`), steps (`08-trail/`), attachments, side threads, memory, appearance, the input area, files and Files (`13-files/`), the chat engine (`14-chat-engine/`: history, work in progress, sending, reading streams, rounds, titling, system prompt, context compaction, and mail — subagent reports and background command endings delivered to whoever should wake), tools (`15-tools/`), APIs and token accounting (`16-api`), settings (`17-settings/`), counting and navigation, export, the Intent (`19-intent/`: the conclusion graph of a piece of work, stored in the folder's `.yan/意.json` and carried across chats — normalizing changes, judging states and regressions, writing text for the model, the evidence registry, reading, writing and attaching, the check before wrapping up, and how the card's graph is laid out and drawn), groups, the audio player, and the browser panel (`26-stage/`). When a part grows large it's split into a subfolder with the same number, whose parts expand in place in name order, concatenating exactly as one file would. Each domain's own state is written at the top of its own part, not piled into `00-state`. `types.d.ts` holds global declarations for type checking and isn't loaded at runtime |
| Registries | The places where Yan is extended are each a table, and adding something is adding one entry: **tools** (`src/15-tools/`, one file per tool: who it's for, whether it can run in parallel, whether it has side effects, how it runs, how its step is drawn, the summary carried to the next question; words delivered from outside mid-answer — follow-ups, reports, messages — are also registered here, with `replay` giving the message it sends the model, so delivering on the spot and rebuilding the answer later (next question, continuing, compaction transcripts all go through `answerParts`) take the same path, and whatever can be delivered can be rebuilt; the definitions given to the model, execution, step cards and sources are all derived from this table, with a description written in `prompts/tools.js`), **model APIs** (`PROVIDERS` in `server/model/`: where to send, which headers, how request bodies and event streams are converted, how models are listed, whether levels have a fixed table; the page only speaks OpenAI chat.completions), **settings tabs** (`SETTINGS_TABS` in `src/17-settings/00-panel.js`: drawing and event wiring as a pair, with panels allowed to live in their own domains), **system prompt** (the `order` table at the end of `prompts/assistant.js`), **text embeds** (`EMBEDS` in `src/04-markdown/00-markdown.js`: which fence it recognizes, the placeholder while half-written, how it looks when complete, the step that runs once it's on the page; interactive web pages are one entry), **file kinds** (`FILE_KINDS` in `src/13-files/00-kinds.js`: extensions, category, icon, how the previewer shows it, how text is extracted), **overlays** (`LAYERS` in `src/03-ui-utils.js`: Esc closes the topmost open layer, each layer registered in its own part), **menus** (`openMenu`: a list of items, with each button and what it does from the same entry), **message actions** (`MESSAGE_ACTIONS` in `src/07-message-actions.js`), **evidence** (`ANCHOR_KINDS` in `src/19-intent/05-anchors.js`: what an Intent item holds on — the syntax, how often its fingerprint is taken, how it's taken, how it's described to people, and whether it covers a given changed file; one entry each for file, folder, probe and test). A new feature starts by asking which table it's an entry in; if none, make the table first and then add the first entry |
| `styles/` | Styles, split by layer (base and themes, layout, welcome page, chat, text content, files, input area, settings, steps, components, motion and responsiveness, the paper-and-ink skin); the order is the cascade order |
| `i18n/` | The interface's English translation table `en.js`: keys are the Chinese source text on screen (with variables written as `{0}`; `{0\|question\|questions}` in a translation picks singular or plural by number). Text shown to people is written as `t("…")` or `` t`…${x}…` ``; whole-sentence errors returned by the bridge go through `tr()` where they're displayed (toasts, errors in chats, settings status lines), while logic still matches the Chinese source. Seals and text for the model aren't in the table. It's loaded by `theme-boot.js` only when English is chosen; `test/i18n.mjs` lists untranslated text on screen |
| `prompts/` | Built-in prompts and tool descriptions, placed first when concatenating `/support.js` (outside the closure); see its README |
| `server.js` · `server/bus.js` · `server/model/` · `server/web.js` · `server/search.js` · `server/headless.js` · `server/http.js` · `server/work/` · `server/chats.js` · `server/store.js` · `server/files.js` · `server/video.js` · `server/sandbox.js` · `server/mcp/` · `server/skills.js` · `server/env/` · `server/mirror.js` · `server/stage.js` · `server/platform.js` · `server/headless-proxy.js` · `server/checkpoints.js` · `server/timers.js` · `server/usage.js` | The local bridge. `server.js` handles access control, the API table, static files and concatenation. `server/bus.js` is the bus (one event stream per page; responses to long requests all return over it, so a page holds only one connection open and isn't limited by the browser's six-connections-per-origin cap). `server/model/` forwards to models (test connection, list models, chat; one registry entry each for OpenAI compatible, Anthropic and ChatGPT subscription; the skeleton for converting other providers' event streams back into chat.completions chunks is in `sse.js`, and each provider only says what each event becomes). `server/web.js` handles web access (address gate, reading pages, calling APIs; public requests go only through `fetchPublicResponse`). `server/search.js` handles search (several sources registered as a table and tried in order, moving to the next when results are off-topic). `server/headless.js` is the headless browser used as a fallback for search and page reading (local Edge / Chrome, started on demand and closed after three idle minutes, with every request in the page passing the address gate). `server/http.js` is the shared JSON reading and writing, 400 errors, streamed uploads and atomic writes for all APIs. `server/work/` is the agent API (`index.js` placement and sandbox screening, the command and background command APIs, and assembling the rest; `files.js` write, read, edit, download; `find.js` listing and search; `intent.js` reading and writing the Intent and content fingerprints; `paths.js` inside or outside the folder and escaping links; `text.js` reading encodings; `shell.js` starting commands, reclaiming process trees and background commands; `locks.js` write locks per file; `atomic.js` atomic writes via temporary file and replace; `picker.js` the system picker (folders and files)) and the Files API (`archive.js`: list, save, fetch, delete). Then the chats API (read all, save, delete), the attachments API (save, fetch, delete, clean) and the storage folder (reading and writing settings, moving; not while a chat is answering); the MCP server pool (starting and connecting external servers, listing and calling tools); skills (`skills.js`: recognizes the single `技能/` under the storage root in SKILL.md format, lists them, reads only files inside a skill folder, saves and deletes); the sandbox environment (install, inspect, clear, and hooking it into processes the bridge starts); video remuxing (containers the browser can't read are remuxed into MP4 with the environment's ffmpeg); adaptive download sources (`mirror.js`: shared by the environment and the browser panel, comparing a slice from the mirror and the official source); the browser panel's connection (`stage.js`: adding the debugging port and allowed origins for Playwright, and looking up the debugging address for the page); the few things that touch the system (`platform.js`: opening web pages and files, showing in the file manager, reclaiming process trees, finding local browsers, reading the system proxy; one version each for Windows and macOS); the local proxy for the headless browser (`headless-proxy.js`: connecting only to verified IPs); checkpoints (`checkpoints.js`: before an answer first changes files, record what the folder looks like so it can be rolled back as a whole; files are stored once by content hash, without git); timers (`timers.js`: scheduled times are kept under the storage root and handed to the page when due, surviving restarts); the usage book (`usage.js`: the page reports increments, added per day and per kind into 用量.json). The sandbox's three screens (commands, paths, environment variables) are pure functions in a part of their own |
| `test/` | `npm test` first runs `test/unit/` (Node's built-in `node --test`, concatenating `src/` and testing pure functions in Node: tool argument repair, stream segmentation, diff counts, token accounting, thinking levels, read-only commands, output trimming, sandbox screening… done in seconds), then end-to-end tests: it starts a fake model API, a test bridge and headless Edge / Chrome, and runs the cases one by one (chat, agent, the two modes together with Files, subagents, side threads, memory, groups, tokens and history, forms, robustness, bridge security). Aimed at Windows; other platforms aren't adapted. Every push to `main` and every PR runs unit tests, type checking and format checking on Windows via GitHub Actions (`.github/workflows/ci.yml`), and that job gates merging; end-to-end and macOS unit tests run on a trial basis and don't block |
| `pack/` | The Windows portable package: `pack.mjs` packs the files needed to run, the official Node and the launcher `言.exe` (`launcher.cs`, compiled with the system's csc) into `dist/yan-<version>-win-x64.zip`; see [Getting started](start.md) |
| `build.js` | The concatenation rules (shared by the bridge and unit tests). `npm run format` unifies formatting with Prettier, and `npm run check` type-checks with `tsc --checkJs` (the page by `jsconfig.json`, the bridge by `jsconfig.server.json`). Prettier is fetched temporarily via npx, and TypeScript and Node's type definitions are installed into an untracked node_modules (`--no-save`), only for development — never at runtime and never as dependencies |

For how the built-in prompts are written, their concatenation order and the split between light and heavy, see [`prompts/README.md`](../../prompts/README.md) (in Chinese).
