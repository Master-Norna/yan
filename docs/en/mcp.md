# MCP

[← Docs](README.md) · [中文](../mcp.md)

Connect external MCP servers in **Settings → MCP** and their tools become available to the model. One card per server: add, edit in place (a local program takes a command, arguments, working directory and environment variables; a remote server takes a URL and headers), disable, reconnect, delete, and expand to see its tools. You can also **Edit as JSON** for the whole configuration. The format is the same as Claude, Cursor and others, so a snippet from a server's README or an existing `.mcp.json` in a project can be pasted in whole:

```json
{
  "mcpServers": {
    "local-server": { "command": "npx", "args": ["-y", "@someone/mcp-server"], "env": { "API_KEY": "…" } },
    "remote-server": { "url": "https://example.com/mcp", "headers": { "Authorization": "Bearer …" } }
  }
}
```

- A local program takes `command` / `args` (optionally `cwd`, `env`); the bridge starts the process and speaks stdio. A remote server takes `url` / `headers` and uses streamable HTTP; servers on the old HTTP+SSE transport add `"type": "sse"` (if `type` is omitted and the streamable HTTP handshake gets a 4xx response, Yan retries once with legacy SSE). On Windows, `.cmd` launchers such as `npx` and `uvx` start fine: `%NAME%` in their arguments is expanded the way cmd does it (a value containing spaces no longer splits the argument), but substring and replacement forms such as `%NAME:~0,5%` or `%NAME:a=b%` are passed through unchanged.
- Optional fields: `disabled` disables it; `autoApprove` lists tool names that skip approval; `readOnlyTools` lists the tool names you have verified as read-only (a server's own hint does not count); `timeout` is how many seconds a single call may wait (default 600; progress reports from the server extend the idle wait, but each call has an absolute limit of twice the configured timeout); `load` sets how it's handed to the model; `note` (**Note to the model** on the card) is a sentence or two you write for the model, placed in the system prompt before the server's own instructions — for conventions the model can't know on its own, like "when I say open the browser, I mean this one" or "this is my composition project".
- How it's handed to the model: servers with few tools are laid out tool by tool, no different from built-in tools (named `mcp__server__tool`); servers with many or heavy tools (definitions over twelve thousand characters in total) get only a directory, plus two tools `mcp_describe` (look up parameters) and `mcp_call` (call), so each question carries just one directory more. `load: "inline"` / `"lazy"` forces either. Instructions the server provides at handshake go into the system prompt, ahead of the skills directory and the drawing and writing notes.
- Approval: whether a tool is read-only is your call — tools listed in `readOnlyTools` are called directly, can run in parallel with adjacent read-only calls, and are available in side threads; a server's own `readOnlyHint` does not count, so it cannot excuse itself from the prompt (Yan’s browser is the bundled Playwright and is judged by its own annotations). Other tools ask for approval each time under **Ask first** (the request shows the server, tool and arguments). Under **Auto-review**, if a reviewer is enabled, non-read-only calls to external servers are reviewed; Yan’s browser uses its own rules for actions that might send data out. Tools listed in `autoApprove` skip the prompt under **Ask first**, and on ordinary external servers they also skip this MCP review under **Auto-review**. **Full auto** neither asks nor sends calls for review.
- Text and text resources are passed through. Images appear as thumbnails in **Steps** and accompany the tool result for models that accept images. Audio, resource links and binary resources get a note. Results with only structured content are given as JSON.
- When a server reports that its tools changed (`notifications/tools/list_changed`), the bridge refetches them and the page takes the new list at its next turn, so the catalogue and parameter schemas handed to the model move with it. An internal refetch doesn't count as delivered: the flag is cleared only when the page fetches, or new tools and schemas would never arrive. When a local server saves an image to a file and returns only a file link (a screenshot taken with an explicit filename, say), the bridge can read it back as an image result (up to four images, up to 8 MB each), so it reaches the step thumbnail and the model just like an inline image.
- Secrets: environment variables and headers whose names look like secrets (key, token, secret, auth, pat…) are masked as `******（已隐藏）` (hidden) in both the card form and the JSON. On save, the placeholder keeps the original value; only a changed value replaces it. **Show secrets** reveals the originals. Exported backups drop `env` and `headers` entirely.
- The model can read and change this configuration itself too (`mcp_config`): it lists each server and its connection state (secrets are masked unless it explicitly asks for the originals), adds or edits by name (send only the keys that change; `env` / `headers` merge by key and a value of `null` removes one), removes and reconnects servers. Under Ask first, writing this configuration asks you first — that section holds commands and arguments, and a local server runs as a process with your permissions; with review on in Auto-review it goes to the reviewer; Full auto changes it directly. A newly added server joins the tool list on the next question.
- Local MCP servers run with your permissions outside Yan's command sandbox; remote servers run at the other end. Local servers inherit the bridge's tool environment: the prepared tools on Windows, if present, and system tools on macOS.
- Layers: `server/mcp/transports.js` only sends and receives (stdio, streamable HTTP and old SSE look the same), `server/mcp/client.js` handles the protocol (handshake, pagination, timeouts, cancellation, server notifications and requests), and `server/mcp/index.js` reuses connections by name. On the page side, `src/15-tools/60-mcp.js` registers the tools in the registry. Connecting a new kind of server only changes configuration, not code.
