# Permissions and sandbox

[← Docs](README.md) · [中文](../sandbox.md)

The local bridge listens only on `127.0.0.1` and only accepts requests addressed to the local host (against DNS rebinding), so other websites can't borrow even model forwarding. Every command is visible; permissions have three levels, **Ask first** / **Auto-review** / **Full auto**, asking before each command by default. A sandbox is on by default (strict under **Ask first**, where blocked commands turn into requests; **Auto-review** and **Full auto** only guard the system itself). Exported backups never include API keys.

## Three permission levels

Commands have three permission levels. In both modes you can cycle through them next to the input box; the tag on the welcome page and **Settings → Tools** set the default for new chats.

- **Ask first** (问而后行): clearly read-only development and system checks run directly (pure display pipelines such as Select / Sort / Format / JSON are allowed); everything else floats an approval request above the input box, where you can **Run**, **Skip** or switch to **Full auto**.
- **Auto-review** (审而后行): no pop-ups; the bridge reviews on your behalf. Routine development, dependency installs, Git (including resets and cleanup), network access, processes, machine-wide inspection and writing outside the working folder are all allowed. Only actions that clearly harm the system or are hard to undo are refused on the spot: privilege escalation, account / service / firewall / security settings, disk and boot configuration, obfuscated commands, deleting whole folders, writing into system folders such as Windows / Program Files. With review turned on under **Settings → Roles**, the steps the rules flag (commands that would be refused above; outgoing requests whose URL carries a long parameter you never gave, or that POST content out; writing into the skills folder; MCP write operations — for the built-in Browser only going to a URL with a long parameter, typing a long passage you never said into a page, uploading files and running code in the page; clicks, keys and paging are not reviewed) go to a separate review model instead, which judges them against what you actually said: it sees only your own messages, the intent's goals and guards, and the step about to run — not page or file contents, and not what the main model says. Approved steps run; refused ones send the reason back to the main model to try another way, still without a pop-up, and after three refusals in a row (or twenty in one answer) it is told to stop and explain to you. If the review model can't be reached, the rules apply as before. Three things stay refused even when review approves, as a floor: touching the config, backups and sign-in files in the storage root; commands that call Yan's own bridge (its endpoints skip approval and the sandbox); and obfuscated or dynamically assembled commands (the reviewer can't see what they'd actually run).
- **Full auto** (径行): no review layer at all.

The three go from strict to loose: Full auto ≥ Auto-review ≥ Ask first, and the sandbox is strict or loose by level too (see below). The one exception is Auto-review with review turned on: system-level actions can run once the reviewer approves them, while Full auto doesn't review, so with the sandbox on it never does them — the most basic protection when nothing asks or reviews. File tools run through the local bridge.

## Sandbox

Commands and file tools in both modes run inside a sandbox enforced on the bridge side, which the model can't get around. It's always on, with a single master switch in **Settings → Tools**. The sandbox has two levels by permission.

The **loose level**, for Auto-review and Full auto, only guards the system itself: the registry, services, scheduled tasks, firewall, accounts, disks, privilege escalation, execution policy, obfuscated commands and aliases, and writing into system folders such as Windows / Program Files. Network access, writing outside the folder, reading `.env` and changing `.git` internals are allowed, and file tools follow **File tool reach**.

The **strict level**, for Ask first, has the three gates below. Commands the strict sandbox would block aren't refused outright: they still float an approval request stating why they'd be blocked, and once approved that one runs outside the sandbox, with "outside sandbox" noted on the step. The three gates:

- **Folder**: *changes* stay inside the working folder or Files (writing, deleting, moving and redirection never use `..` to climb up, `~`, `$env:USERPROFILE` or absolute paths outside the folder), while *viewing* can reach the whole machine — checking a computer means looking through system folders, the registry, processes and logs, and locking reads would block that entirely. File tools still stay inside the folder and ignore **Anywhere**. Reading and writing `.env`, keys and credential files is refused, `.git` internals aren't written, and search skips secret files.
- **Commands**: anything that touches the system (registry, services, scheduled tasks, firewall, accounts, disks, shutdown, privilege escalation, execution policy), hides what it does (encoded commands, `Invoke-Expression`) or connects out directly (`curl` / `iwr` / `wget`; pointing at local 127.0.0.1 is allowed) is refused. Install dependencies through a package manager and look things up with the search tools.
- **Environment**: commands can't see environment variables whose names look secret (KEY / TOKEN / SECRET / PASSWORD…).

A command refused at the loose level comes back to the model with a reason; rewriting it accordingly is enough. Connecting out only counts forms that really go online (`[System.Net.…]`, `New-Object Net.…`); something like `rg HttpClient`, which only searches text, doesn't.

One more rule ignores both the permission level and the sandbox switch: in the storage root, `配置.json` (which holds your API keys), the `配置备份/` backups and `ChatGPT 登录.json` are off limits to file tools, search and commands. If the model could read them, a single line on a web page or in a document could trick it into putting a key into a URL and sending it away; if it could write them, it could turn off its own sandbox or change presets. Change settings in Settings. Only the bridge's current storage root counts; files with the same names elsewhere are unaffected.

This is static screening, not process isolation: code inside scripts still runs with your permissions (whatever is in `node -e`, `python -c` or a script file isn't screened; a script that assembles the bridge address at runtime can call the bridge's API too — which grants nothing beyond what the script itself already has, so the rule about the bridge port only blocks naming it directly). Processes started with `Start-Process` detach from the process tree, and neither stopping nor timeouts can reclaim them. Deciding "does this command change anything" relies on a list of verbs (`Set-Content`, `Remove-Item`, `copy`, `move`, `md`, redirection…); forms outside the list slip through, leaving only the three permission levels as the backstop. Permission levels and the sandbox are independent: with the sandbox off, Auto-review still refuses what it judges harmful to the system, only Full auto drops that layer, and file tools follow only the **File tool reach** setting at both of those levels. A foreground command that runs past its `timeout` (default 120 seconds, at most 600) isn't killed; it moves to the background and wakes the model when it ends (see [Chat and Agent](work.md#file-tools)); use **Stop** to reclaim it. Since viewing is open to the whole machine, ordinary files outside the working folder (browser data, chat logs and so on) are within the model's reach — only `.env`, keys and credentials, recognizable by name, have their own rule. Don't point the working folder at a place you don't want changed.

The **Tools** tab in settings governs everything about what the model may act on: the sandbox, the default command permission level for new chats, **File tool reach**, **Model can read Files**, and **Tool round limit** (counted in rounds; several concurrent calls in one round count as one; blank means unlimited).
