# Attachments and Files

[← Docs](README.md) · [中文](../files.md)

- Click, drag in or paste images, text, code, PDF, Office and other files. PDF, DOCX, PPTX, XLSX and the like have their text extracted locally in the browser first; images are sent as visual content. Small PDFs without extracted text can still be sent as files if the API supports PDF; other binary formats generally get a file note instead
- Attachment originals are stored with the chat in the storage folder's `附件/` (if writing to disk fails, they wait in the browser's IndexedDB and are pushed into the folder once the bridge reconnects). Up to 256 MB per file and at most 10 files per send; files over 32 MB without extracted text are not sent to the model whole — like archives, the model gets the local path and reads it with its tools; deleting a chat or removing an attachment clears originals that are no longer referenced; cleanup also removes leftover unreferenced originals stored for at least a day. Files saved into Files can also be up to 256 MB each. The PDF parser and CJK character maps ship with the project
- **Files** (卷宗) keeps frequently used files across chats. Files is the storage folder's `卷宗/` (by default `~/.yan/卷宗/`), and the Files page is a view of that folder. Files dragged in (only from outside the page; dragging an image within Files or an attachment in the input area doesn't save another copy; dragging in a folder recreates it as is, renaming duplicates and skipping names starting with a dot; the input area takes only files, so drop folders into Files), files saved with **Save to Files**, and outputs the model writes in chats with no bound folder all land here. You can click a row to preview it; hover the row's tail for Download, Rename and Delete, each drawn as a small brush icon. To send one with a message, choose **Files** from the input box's **＋**. Scripts and intermediate files the model writes to produce an output go in a hidden folder `.草稿/<chat id>/` inside Files, which the page doesn't list; they're cleared when the chat is deleted, and the top of the Files page also offers "n scratch folders · size · Clean up". An answer's outputs are the local files its reply links to: the model writes the report, table or image it is handing you as a link (`[report](report.md)`), in both modes, and the outputs card at the end of the answer lists those (noting **saved to Files** when they're in Files). Which files appear is the model's choice, so a pile of unzipped files, code it touched along the way, or files another chat wrote into Files at the same time don't creep in. One line each — type, file name, size, with a small brush Download key at the row's tail; click the row itself to preview it, and the link in the reply opens the same preview. If you later delete one from Files, its line stays but is marked **Removed from Files** and is no longer clickable. The preview is in-place and floating, no download needed: images shown directly, PDFs in the browser's built-in reader, CSV / TSV as tables, Markdown rendered, text and code as is, DOCX / ODT, XLSX / ODS and PPTX / ODP extracted locally into structured previews (headings, lists, tables, worksheets and slides; presentations show one slide at a time, with a row of vermilion dots underneath (one per slide, fading and shrinking away from the current one); click a dot or use the left/right arrow keys to page; PPTX uses the original slide aspect ratio and extracts titles, text boxes, speaker notes, and supported embedded images), without reproducing the original layout; legacy DOC / XLS / PPT cannot be previewed this way; web pages in the same isolated sandbox as in-page visuals, without network or this site’s identity; clicking a row on the Files page opens this same preview. Images and links in Markdown resolve from the folder the file is in; if the document or image has moved and the path no longer works, the nearest file with the same name is used (no guess when several are equally near), the file itself is left unchanged, and an image still not found leaves its caption. Documents in Files (PDF, Office, text) are readable from every chat in both modes: the model reads them with `read_document`, fetched and extracted locally only when used; turn off **Settings → Tools → Model can read Files** to remove this document-reading entry point. **Export** in a chat's **⋯** menu in the sidebar saves the whole chat as Markdown (with step summaries and outputs) into Files. Search by name and filter by image / document / audio / video / archive; deleting a chat never deletes its outputs from Files
- Listen: opening audio in Files or in attachments (click a Files row, or **Preview** on an attachment) opens the audio player — a track drawn as a single brush circle (ensō), the stroke thickening and thinning with loudness, the brush tip marking the present; previous and next track (audio in the same place forms a list, playing on to the next, and wrapping to the first after the last). Clicking outside or pressing Esc minimizes it: the music keeps playing, and a thread of ink drops from the top right of the text with a small circle that sways with the sound; click it for a paper tag (title, time, previous / next, play / stop), and click the title to return to the full view. Only the × on the full view stops playback. There is a single resident player on the page; anything else that wants to play audio just hands a track to `listenLoad` (`src/25-listen.js`)
- In a multi-turn chat, only the message being answered carries attachment originals, plus the images of the most recent earlier question that had any (sent whole, so "that image just now" can still be answered). Earlier text and extracted content keep their first 3,000 characters. Older images and ordinary binary files become placeholder notes, while archives can still include a local path. To let the model see an old image again, attach it from Files again
- Text attachments and extracted content in the current turn have a per-file cap: about 15% of the model's window, with a minimum of 4,000 tokens (24,000 tokens if no window is set). Anything larger is sent only as one line, "file name, character count", and the model reads it by page or keyword with `read_document` instead of stuffing a whole book into the prompt and overflowing the window. A token-count estimate is recorded when the attachment is stored, and the context counter at the lower right uses it
